# Oracle Review: Product & UX Architect

**Reviewer:** Kimi (Product & UX Architect persona)  
**Date:** February 8, 2026  
**Documents Reviewed:** Sections 01-09, Competitive Landscape Research

---

## Executive Summary

Redan has strong technical foundations and a compelling security story, but the MVP planning underestimates the friction between "technically correct" and "actually usable." The current design optimizes for security purity at the cost of developer velocity. The first-run experience has multiple failure points that will cause 60%+ of developers to abandon before their first successful session. The configuration model requires too much upfront knowledge. The "env backend only" MVP creates a weak security story that undermines the core value proposition.

**Overall assessment:** The product needs a "pit of success" redesign—sensible defaults that make the secure choice the easy choice, with progressive disclosure of advanced features.

## 1. First-Run Experience Analysis

### Current Happy Path (Section 5.3 Walkthrough)

**Step 1-2: Install & Verify**  
`curl -sSf https://redan.dev/install.sh | sh`

**UX Impact: 🔴 Blocks adoption**

**Problems:**
- No mention of prerequisites check. What if libkrun isn't installed? The install script must handle this, but there's no spec for graceful fallback.
- macOS users need Homebrew libkrun installed first. Linux users need KVM enabled. The install script can't fix hardware virtualization.
- The `curl | sh` pattern triggers security-conscious developers. No alternative (brew install, apt install, cargo install) is documented.

**Fix:**
```bash
# Install script should detect and report:
$ curl -sSf https://redan.dev/install.sh | sh
✓ Detected macOS 14.2 (Apple Silicon)
✓ Homebrew found
→ Installing libkrun via Homebrew... done
✓ libkrun 1.6.0 installed
→ Downloading redan 0.1.0... done
✓ redan installed to ~/.local/bin
⚠️  First run: Run 'redan doctor' to verify your system
```

---

**Step 3-5: Navigate & Initialize**  
`redan policy init`

**UX Impact: 🟠 Slows adoption**

**Problems:**
- `policy init` is a confusing command name. Developers think "I want to run something securely," not "I need to write a policy."
- The generated redan.toml (Section 3.3) is 80+ lines with nested sections. Overwhelming for first use.
- No interactive wizard asks "What are you trying to do?" to generate appropriate defaults.

**Fix:**
```bash
$ redan init  # renamed from 'policy init'
? What agent are you using? [Claude Code]
? What package manager? [npm]
? Does this project need API access? [GitHub, OpenAI]
✓ Created redan.toml with 3 allowed hosts and 2 secrets
? Run 'redan exec -- claude' now? [Y/n]
```

The generated redan.toml should be ~10 lines for this use case, not 80.

---

**Step 6: Verify Secrets**  
`GITHUB_TOKEN=ghp_xxx redan secret test`

**UX Impact: 🔴 Blocks adoption**

**Problems:**
- This is the moment of failure for most users. The env backend requires the developer to have secrets already exported. But if they're using Redan to solve the "secrets in env" problem, this creates circular logic.
- The command requires prefixing every session with secrets. Developers will immediately create a wrapper script or shell alias, defeating the security model.
- No guidance for "I don't have a GITHUB_TOKEN yet" or "I use 1Password/aws-vault/direnv."

**Fix:**
Add a `redan login` command that integrates with common secret sources:
```bash
$ redan login github
? How do you store GitHub tokens? [1Password / GitHub CLI / env / skip]
→ Found 'GitHub' item in 1Password
✓ Configured GITHUB_TOKEN (backend: 1password)
# Now 'redan exec' works without env prefix
```

---

**Step 7: Run**  
`redan exec -- claude`

**UX Impact: 🟡 Friction**

**Problems:**
- Boot time of 148ms is optimistic (Section 2.2). Real-world with OCI image pull is 30-60 seconds on first run. The "(148ms)" message is misleading—it doesn't include image pull time.
- If the image pull fails (network timeout, auth required for private registries), the error is likely a cryptic libkrun or OCI error.
- "mounted ./ → /workspace" assumes the developer understands virtio-fs. They don't.

**Fix:**
```
$ redan exec -- claude
→ Pulling Ubuntu 24.04 base image... 45s (first time only, cached after)
→ Starting secure environment... 200ms
✓ Project mounted at /workspace
✓ Network: 3 hosts allowed (github.com, npmjs.org, openai.com)
✓ 1 secret ready (GITHUB_TOKEN)
✓ Claude Code starting...
```

## 2. Configuration Complexity

### Current redan.toml (Section 3.3)

**UX Impact: 🔴 Blocks adoption**

The full example in 3.3 is ~80 lines with:
- 5 different sections with nested tables
- 4 different secret backends demonstrated
- Network allow/deny lists
- Audit configuration
- VM resource specs

A first-time user seeing this thinks: "This is a production infrastructure tool, not a development tool."

### Minimum Viable Config

What a developer actually needs for MVP:

```toml
# redan.toml - generated by 'redan init'
image = "ubuntu:24.04"

[network]
allow = ["api.github.com", "registry.npmjs.org"]

[secrets.GITHUB_TOKEN]
source = "env"  # or "1password", "vault", etc.
for = "api.github.com"
```

That's it. 6 lines. Everything else (cpus, memory, audit, mounts) should have smart defaults.

### Zero-Config Mode

**Missing from planning:** Redan should work with zero configuration for the 80% case:

```bash
$ cd my-project
$ redan exec -- claude  # no redan.toml exists
⚠️  No redan.toml found. Using defaults:
    - Image: ubuntu:24.04
    - Network: GitHub + npm registries allowed (auto-detected from package.json)
    - Secrets: None configured
→ Create redan.toml to customize: redan init
✓ Starting with defaults...
```

Auto-detection from project context:
- `package.json` → allow npm registries, use node image
- `requirements.txt` → allow pypi.org, use python image
- `.git/config` → allow github.com/gitlab.com

## 3. Error UX Design

### Scenario: Host Blocked

**Current behavior (speculated):**
```
redan: ✗ blocked connection to evil.com:443 (not in allowlist)
```

**Problem:** The developer sees this but Claude is trying to do something. Is it malicious? Is it necessary? What do I do?

**Fix:**
```
redan: ✗ Blocked connection to api.npmjs.org:443
   
   Claude Code tried to reach 'api.npmjs.org' which isn't in your allowlist.
   
   To fix this, add to redan.toml:
   [network]
   allow = ["api.npmjs.org"]
   
   Or run with: redan exec --allow api.npmjs.org -- claude
   
   [?] Allow just this session? [y/N/skip forever]
```

Interactive resolution at the point of failure.

---

### Scenario: Secret Backend Unreachable

**Current behavior:** Likely a Rust error trace or "connection refused."

**Fix:**
```
redan: ✗ Can't reach Vault at https://vault.company.com
   
   Your redan.toml configures Vault for the DATABASE_URL secret,
   but the server is unreachable (timeout after 5s).
   
   Common fixes:
   1. Connect to company VPN
   2. Check VAULT_ADDR environment variable
   3. Use local secret instead: redan exec --secret DATABASE_URL=local -- claude
   
   Run 'redan secret test' for full diagnostics.
```

---

### Scenario: VM Boot Fails (No KVM/HVF)

**Current behavior:** Likely a low-level libkrun error.

**Fix:**
```
redan: ✗ Cannot start secure environment
   
   Hardware virtualization isn't available on this machine.
   
   macOS: Install Rosetta 2? No, that's not it. Check:
   - System Settings → General → "Allow applications to run in background"
   - libkrun requires macOS 14+
   
   Linux: Check KVM:
   $ sudo usermod -aG kvm $USER  # then log out and back in
   $ sudo modprobe kvm
   
   Or run without VM isolation (less secure):
   $ redan exec --no-vm -- claude
```

---

### Scenario: MITM CA Rejected

**Current behavior:** Certificate error in npm/pip/cargo.

**Fix:**
```
redan: ✗ npm failed with "certificate has expired"
   
   npm doesn't trust the Redan security certificate. This is common
   with tools that bundle their own certificate store.
   
   Quick fix for this session:
   $ NODE_EXTRA_CA_CERTS=/etc/redan/ca.crt npm install
   
   Permanent fix:
   $ redan config set npm_compatible true  # auto-sets env vars
   
   [?] Disable certificate verification for npm? (less secure) [y/N]
```

## 4. Adoption Funnel Analysis

| Stage | Barrier | Impact | Fix |
|-------|---------|--------|-----|
| **Awareness** | "Another security tool? I already have Docker." | 🟡 Friction | Position as "Docker for agents" — familiar mental model |
| **Interest** | "microVMs? libkrun? This sounds like infrastructure." | 🟠 Slows | Lead with outcome: "Run Claude without giving it your SSH keys" |
| **Install** | curl\|sh resistance, libkrun dependency | 🔴 Blocks | Provide brew/apt/choco packages; handle deps automatically |
| **First use** | redan.toml complexity, env backend weakness | 🔴 Blocks | Zero-config mode; `redan init` wizard; better env story |
| **Repeat use** | Boot time, typing secrets every session | 🟠 Slows | Warm pool (v1.1); `redan login` for secret backends |
| **Team adoption** | No team policy sharing, no central config | 🟡 Friction | `redan team init` that creates shareable team configs |

**The "aha moment":** When a developer sees `redan: ✗ blocked connection to evil.com` after a prompt injection attempt, and realizes their credentials were safe. This needs to happen within the first 3 sessions or they churn.

## 5. Competitive DX Comparison

### vs. Just Running the Agent (No Sandboxing)

| Factor | No Sandbox | Redan MVP |
|--------|-----------|-----------|
| Install | None | curl\|sh + libkrun |
| First run | `claude` | `redan exec -- claude` + config |
| Daily use | Same | Same, but prefix with secrets |
| Security | None | Partial (env backend weak) |

**Verdict:** At MVP, Redan is strictly more friction for uncertain security gain. The story gets stronger with Vault/1Password backends (v1.0), but MVP is a hard sell.

### vs. E2B (Cloud Sandbox)

| Factor | E2B | Redan |
|--------|-----|-------|
| Install | `pip install e2b` | curl\|sh + libkrun |
| First run | 3 lines of Python | config file + env vars |
| Network | Allowlist via API | TOML config |
| Secrets | In VM (visible) | Network injection (invisible) |
| Cost | Usage-based | Free |
| Session limit | 24 hours | Unlimited |

**Verdict:** Redan's only clear win is "free" and "unlimited." The DX is worse. The security is better but invisible.

### vs. Docker

Developers know Docker. They'll ask: "Why not just `docker run --rm -v $(pwd):/workspace -e GITHUB_TOKEN claude`?"

Answer needs to be crisp:
- Docker shares the kernel (weaker isolation)
- Docker containers see your Docker socket (host access)
- No network-layer secret injection in Docker
- Redan is purpose-built for agents, not general containers

**But:** The `docker run` one-liner is compelling. Redan needs to match that simplicity: `redan exec -- claude` should "just work" with auto-detected config.

### vs. Claude Code's Built-in Sandbox

`srt` (sandbox-runtime) is already installed with Claude Code.

**Usage:** `claude --sandbox` (or auto-enabled in some modes)

**Verdict:** This is the real competitor. Claude's sandbox is:
- Zero additional install
- Zero configuration
- Good enough for most cases
- Maintained by Anthropic

**Redan's differentiation must be:**
1. Works with ANY agent (Codex, Cursor, Pi), not just Claude
2. Enterprise secret management (Vault, AWS SM)
3. Network policy that can't be bypassed (HTTP_PROXY vs VM boundary)
4. Single binary, no Node.js/npm dependency

## 6. The "Env Backend" Trap

**The Core Contradiction:**

MVP only supports `source = "env"`. This means:
1. Developer exports `GITHUB_TOKEN=ghp_xxx` in their shell
2. Developer runs `redan exec -- claude`
3. Redan reads the env var, generates a placeholder
4. Placeholder goes to VM
5. Real value injected at network layer

**What's the security win?**

The planning documents claim "agent cannot read real secret from environment" (invariant I-3). But the developer still had to export the real secret to run Redan. If their shell is compromised, the secret is there. If they type it on the command line, it's in shell history.

**The honest MVP story:**
> "Redan MVP prevents the agent from accidentally logging or exfiltrating your secrets via prompt injection. It doesn't protect against a compromised developer workstation—that requires Vault/1Password backends (coming in v1.0)."

**This is a weak pitch.** It concedes that Redan MVP is a "better Docker run" not a "security transformation."

**Recommendation:** Either:
1. **Move 1Password CLI backend to MVP.** It's the easiest "real" backend and completely changes the story: "Redan integrates with 1Password so your tokens never touch shell environment or disk."
2. **Or, be honest in messaging:** Position MVP as "Docker alternative with network policy" not "secure secret management."

The current planning tries to have it both ways and will confuse users.

## 7. Documentation & Messaging

### Current Framing Problems

**"microVM"** — Means nothing to 95% of developers. It's infrastructure jargon.

**"libkrun"** — Implementation detail that shouldn't be in the pitch.

**"Network-layer secret injection"** — Accurate but abstract. Doesn't convey benefit.

**"redan (n.): a V-shaped fieldwork..."** — Cute but doesn't help adoption.

### Recommended Messaging

**One-sentence pitch:**
> "Run AI agents without giving them your passwords."

**One-paragraph pitch:**
> Redan is a security wrapper for AI coding agents like Claude, Codex, and Cursor. It runs agents in an isolated environment where they can see your code but not your SSH keys, AWS credentials, or GitHub tokens. When the agent needs to call an API, Redan injects the secret automatically—so the agent never sees the real value. Think of it as a firewall between your agent and your identity.

**Tagline options:**
- "Your code, not your credentials."
- "Sandbox for agents, not infrastructure."
- "The agent sees the project. Redan sees the secrets."

**Avoid:**
- "microVM" → use "secure container" or "isolated environment"
- "virtualization" → use "isolation"
- "secret injection" → use "automatic authentication"
- "policy" → use "permissions" or "rules"

## 8. Missing User Stories

### Critical Gaps

**US-M1: Database/Local Service Access**
> As a developer, I run an agent that needs to connect to Postgres/Redis running on my laptop. The agent inside the VM needs to reach `localhost:5432` on the host.

**Current planning:** Blocks localhost by default (Section 4.5). No story for allowing specific host ports.

**Fix:** Add to redan.toml:
```toml
[network.local]
allow_ports = [5432, 6379]  # postgres, redis
```

---

**US-M2: Browser/Headless Chrome**
> As a developer, my agent uses Playwright or Selenium to test a web app. The browser needs to run inside or alongside the VM.

**Current planning:** No GUI/display server in VM. No browser support mentioned.

**Fix:** Document how to run headless Chrome in the VM, or provide `--share-display` flag for host display access (with security warnings).

---

**US-M3: Multi-Repo Agent Work**
> As a developer, my agent needs to work across multiple related repositories (a monorepo or microservices setup).

**Current planning:** Single `/workspace` mount.

**Fix:** Support multiple mounts:
```toml
[workspace]
mounts = [
    { host = "./frontend", guest = "/workspace/frontend" },
    { host = "../shared-lib", guest = "/workspace/shared" }
]
```

---

**US-M4: Team Shared Configuration**
> As a team lead, I want to share a `redan.toml` that works for everyone on my team, with their individual secrets from their own 1Password/Vault.

**Current planning:** redan.toml committed to repo with per-user secret references.

**Fix:** Support user-specific overrides:
```toml
# redan.toml (committed)
[secrets.GITHUB_TOKEN]
source = "1password"
item = "GitHub API Token"  # each team member has their own item

# ~/.config/redan/user.toml (not committed)
[secrets.GITHUB_TOKEN]
op_account = "personal"
```

---

**US-M5: Agent Needs Docker**
> As a developer, my agent runs `docker build` or `docker-compose up` as part of its workflow.

**Current planning:** Explicitly out of scope (Section 5.5).

**Problem:** This is a common workflow. "Use Redan, but not for Docker projects" is a big limitation.

**Fix:** Document Docker-in-Redan as unsupported, but provide `redan exec --allow-docker` that mounts the Docker socket (with big security warnings). Or suggest Colima/Lima as alternatives.

---

**US-M6: CI/CD Integration**
> As a DevOps engineer, I want to run Redan in GitHub Actions to sandbox agent-generated code in CI.

**Current planning:** CI is "out of scope for v1" due to KVM requirements (Section 2.3).

**Problem:** This limits Redan to developer laptops. The security story is weaker if it can't be enforced in CI.

**Fix:** Document self-hosted runner requirements. Provide a GitHub Action that checks for KVM availability and fails fast with clear messaging if not available.

| Priority | Fix | Impact |

**Bottom line:** Redan is technically sound but needs a "developer experience" pass to remove friction from the first 5 minutes. The security model is strong, but only if developers actually use it. Make the secure choice the easy choice.
